# Security scan scope and evidence

Run the same Semgrep version (1.112.0) and security/semgrep.yml against the original source and the final source, exporting JSON. Example inside a mounted working directory: `semgrep scan --config security/semgrep.yml --metrics off --json --output evidence/sast-after.json src`. Use an absolute path to the same rule file when scanning the separate original tree. Record per-rule counts and errors; do not treat parse failures as clean results. Add a broader PHP scan and review its findings separately. Custom rules cover selected code patterns only, not all application vulnerabilities.

The targeted SAST gate intentionally remains red at stage 3 until member 4 removes the level-dependent blog CSRF handler. Do not lower the gate to conceal incomplete remediation. Dependency scanning uses the version-banner inventory generated by scripts/vendor-inventory.py and Trivy sbom; the app has no Composer lockfile. Read docs/DEPENDENCY-COVERAGE.md and inspect both the SBOM and unresolved coverage. An empty dependency inventory does not prove there are no vulnerable libraries. Container scanning separately covers installed image components. Retained third-party libraries may require additional inventory and remediation before completion.

Gitleaks scans Git history. Trivy HIGH/CRITICAL dependency and image findings block. There are no blanket exclusions or continue-on-error settings. A failed scanner job is a finding or tooling problem to investigate, not a passing delivery. Action/tool tags are selected explicitly but image digests and advisory dates must be captured for reproducibility.

The manual gate-demo workflow adds an unsafe sink in an ephemeral checkout and must fail. It never serves that file or commits it. Run it on GitHub after manual submission, record the actual URL, revision, failing step and screenshot. Hosted runs cannot be produced by a local ZIP package.
