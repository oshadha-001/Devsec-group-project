# Muditha IT24610813 CSRF secrets and report integration

At security level 0 the original add-to-your-blog.php creates a CSRFTokenHandler whose validation returns true without checking a token. A request with a victim session can insert a blog entry without proving it came from the legitimate form. This is CWE-352. Modern SameSite cookie behavior may prevent some cross-site demonstrations; record browser and cookie settings instead of claiming every cross-site form succeeds.

This patch validates before insertion, requires an authenticated session, takes the token only from POST, and compares a 32-byte cryptographic session token using hash_equals. The token is independent of Mutillidae's demo security level. Empty, array, wrong-length and another session's tokens are denied. Existing demo token information is replaced by a status message so the page does not unnecessarily print token diagnostics. The session token is stable for multiple tabs and should be invalidated with the session at logout.

Before patching, authenticate as jeremy and submit a unique synthetic blog entry without csrf-token using a local test request. Verify the row was actually inserted. For browser CSRF proof, use an HTML form served from another local port (different origin but same site), include the same submit-button and blog_entry fields, and use the current authenticated browser session. Record that same-site/different-origin condition explicitly. Repeating the same tokenless request after patching must produce rejection and no database row. Also verify a valid form submission succeeds and another session's token fails. Do not confuse missing-token validation with proof that a browser sent a cross-site cookie.
